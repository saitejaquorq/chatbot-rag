# Chatbot RAG

A chatbot with RAG. A gemini styled chatbot with all important features required for a chatbot. 
Core features include
* Document ingestion: upload or sync files (PDF, DOCX, Markdown, HTML, TXT), with status tracking and error reporting
* Chunking and embedding: split documents into searchable passages and convert them to vectors
* Retrieval: semantic search over the chunks, ideally hybrid (vector plus keyword) for better accuracy
* Grounded answer generation: the LLM answers from retrieved context only
* Citations: each answer links back to the source document, page, and snippet
* "I don't know" handling: a graceful response when the documents don't contain the answer
* Chat interface with streaming: tokens appear as they're generated
* Conversation memory: follow-up questions work ("what about the second one?") through query rewriting using chat history
* Document management: list, update, and delete documents, with chunks and vectors removed along with them
* Multi-LLM support: switch models per request, with fallback if a provider fails
* Reranking: a second-pass model that improves the order of retrieved passages
* Metadata filters: restrict answers to certain documents, dates, or collections
* User accounts and workspaces: separate data per user or team, with access control
* Feedback buttons: thumbs up/down on answers, to find weak spots
* Usage and cost tracking: tokens, latency, and spend per model
* Admin view: see what was retrieved and why, for debugging bad answers

Generated by the Quorq AI SDLC platform from an approved app design.

Every screen here was generated from a design the team reviewed and approved.
A backend was also generated for this project (see `../backend/`), but these
screens still run on **seeded sample data** -- wiring a given screen to a real
endpoint is the next job, not something this repository pretends to have done.

## Running it

```bash
npm install
npm run dev
```

`npm run build` bundles the app; it does not typecheck. The screens were generated, and a
generated screen that renders correctly can still not satisfy `tsc` -- usually an untyped
`useState({})` that is then read for named fields. Deployment would fail on that, which is
a poor reason not to ship a working prototype.

`npm run typecheck` runs `tsc --noEmit` when you want it, and is worth fixing before this
becomes a codebase anyone maintains.

## Checks and tests

- `npm run lint` / `npm run lint:fix` -- ESLint over the whole app; `lint:fix` applies the
  fixes it can. The platform runs `npm run lint` as a gate during development, so keep it green.
- `npm run test` -- Vitest component tests, beside the components they cover.
- `npm run test:e2e` -- Playwright acceptance tests from the `e2e/` folder beside `src/`.
  `npm run test:e2e:install` fetches the browser first. With `E2E_BASE_URL` set it runs against
  that deployed URL; without it, Playwright builds and serves this app and runs against that.

## Layout

- `src/screens/` -- one module per approved screen.
- `src/App.tsx` -- the navigation shell and the route table.
- `src/lib/ui.tsx`, `src/lib/icons.tsx` -- the component and icon vocabulary
  the screens were written against.
- `src/lib/brand.ts`, `src/index.css` -- the approved brand, as tokens and as
  CSS variables.
